## What the markers mean

**usable**
The `import` binds and the name has a runtime class or enum behind it, so a script can
construct it, call a static on it, or hold one. This is the default and is left unmarked.

**not usable**
The type is in the build and the `import` line is accepted, but the name answers nothing on
first use. Listed per stack with the reason, and never silently omitted.

*extendable*
The build generated a bridge class for it, so a script may write `class Mine extends That`.
Without one a script still imports and constructs the type, it just cannot subclass it.

*wrapped*
An abstract given a generated runtime form. Abstracts have no class of their own, so without
this its constants and operators resolve to nothing.

### Abstracts wrapped

An abstract has no runtime class of its own, so a wrapper is what gives it constants and
operators a script can reach. This is what the build asked to wrap, which is very nearly what it
got: a `private` abstract is wrapped and then unreachable anyway, since no import crosses a
module boundary to a private type, and one behind a platform gate is wrapped only on that
platform. Six of flixel's are one or the other.

### Not usable

These are in the build and a script can write the `import`, and then the name answers nothing.
Every one was tried and failed. Two causes account for nearly all of them, and only one has a
fix:

- **An abstract with no wrapper** is one no preset asked for. Naming it in a preset's
  `abstracts`, or its package in `abstractPackages`, is what generates one. The exception is a
  `private` abstract, which no `import` reaches from outside its own module whatever is
  generated for it.
- **A function or anonymous shape** has no runtime form to bind at all, so there is nothing to
  turn on. `parity.md` covers what the interpreter does and does not represent.

### Abstracts wrapped

An abstract has no runtime class of its own, so a wrapper is what gives it constants and
operators a script can reach. This is what the build asked to wrap, which is very nearly what it
got: a `private` abstract is wrapped and then unreachable anyway, since no import crosses a
module boundary to a private type, and one behind a platform gate is wrapped only on that
platform. Six of flixel's are one or the other.

### Not usable

These are in the build and a script can write the `import`, and then the name answers nothing.
Every one was tried and failed. Two causes account for nearly all of them, and only one has a
fix:

- **An abstract with no wrapper** is one no preset asked for. Naming it in a preset's
  `abstracts`, or its package in `abstractPackages`, is what generates one. The exception is a
  `private` abstract, which no `import` reaches from outside its own module whatever is
  generated for it.
- **A function or anonymous shape** has no runtime form to bind at all, so there is nothing to
  turn on. `parity.md` covers what the interpreter does and does not represent.

## What this does not promise

**Verified on the target named per stack, and a different target can differ.** Both are targets a
game ships as, hxcpp or HL/C, rather than the interpreter, because dead code elimination is a
property of the target and is what strips a member. What a type *is* does not change with the
target, so an abstract with no wrapper and a typedef of an anonymous shape fail everywhere; a
library defining a type per target, as heaps does with `hxd.FloatBuffer`, is where the two can
disagree.

**Usable is about the type, not every member on it.** Under hxcpp's default `-dce std` a member no
compiled call site happens to use is stripped, and a script reaching it gets `Cannot call null`.
That is a property of how the host was built rather than of this list.

**An `inline` member is never reachable**, at any DCE setting: inlining is a compile-time
substitution, so there is no method to reflect on. Those need an entry in `Config.callShims`.

**Nothing is imported for you.** No shipped preset offers a bare name, so a script writes its
own `import` for everything above, as in Haxe. A host that wants some names bare asks for them
by path with `Boot.importGlobals([...])`, or marks its own classes `@:scriptAmbient`.

**These lists are version-sensitive by nature**, so re-run this after a library upgrade.
